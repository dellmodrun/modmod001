PHP2Shell: RCE in PHP

XLinkedIn 5 min

  2. How to check
  3. What to do

PHP2Shell is two critical vulnerabilities in PHP, CVE-2026-109618 and CVE-2026-109619, that let an unauthenticated attacker run code on servers that use PHP to handle web requests. PHP released fixes on 21 October 2026 and its security team rates both flaws critical (CVSS v4.0 9.2). Exploitation attempts have been reported. Update to PHP 8.5.12, 8.4.27, 8.3.36, or 8.2.35, then restart every PHP worker.

Who is affected

  • PHP 8.2, 8.3, 8.4, and 8.5 are affected before 8.2.35, 8.3.36, 8.4.27, and 8.5.12 respectively, when serving web requests. PHP 8.6.0 release candidates before RC4 are also affected.
  • PHP 8.1 and older no longer get upstream releases. Calif’s analysis, cited by Tenable, traces the earliest affected code path to PHP 5.4.0. PHP has not stated a full affected range.
  • Apache with mod_php is the highest risk, according to PHP. Remote code execution is confirmed for both CVEs, and for CVE-2026-109618 with default input and memory limits.
  • On PHP-FPM, CVE-2026-109619’s session upload progress path was validated as RCE on a normal dynamic pool. For CVE-2026-109618, source analysis says FPM is susceptible, but no complete exploit has been demonstrated.
  • FrankenPHP and LiteSpeed (LSAPI) are susceptible based on source analysis only. No exploit has been validated, and PHP says this does not make them immune.

How to check

  1. List every PHP runtime that serves web traffic: main apps, internal tools, legacy apps, and PHP pulled in by container base images or OS packages.
  2. Check the version that actually serves requests. The CLI (php -v) can be a different build from PHP-FPM or Apache’s mod_php.
  3. For distribution packages, compare against your distribution’s advisory. Backported fixes may not change the upstream version number.
  4. After updating, rebuild and redeploy images, restart PHP workers, and confirm the new version is serving requests.
  5. Review activity from at least 17 October 2026. Look for new or modified PHP files, web shells, unexpected admin users, and unusual outbound connections. Also look for unexpected child processes or shell commands launched by PHP or the web server: exploitation does not need to leave a web shell on disk.
  6. In request logs, AWS suggests looking for multipart POST requests containing the PHP_SESSION_UPLOAD_PROGRESS field.

What to do

  • Update PHP to a fixed version. If you use your Linux distribution’s PHP packages, follow its security advisory. PHP says updating is the only complete fix.

  • If you can’t update straight away, PHP’s advisories list settings that reduce the risk but don’t remove it. Set them administratively, so no pool, directory, or app setting can override them:

    • For CVE-2026-109618:

      • Set memory_limit=-1.
      • Keep post_max_size conservative and enforce request size at the frontend.
      • Lower max_input_nesting_level and bound the number of input variables, multipart parts, and uploads.
      • Block multipart requests at the frontend if your app doesn’t use them.
      • Don’t use RLIMIT_AS or RLIMIT_DATA, which can trigger the vulnerable path.

    • For CVE-2026-109619, set session.upload_progress.enabled=0 and, on PHP 8.5, fatal_error_backtraces=0. If performance allows, PHP also suggests pm.max_requests=1.

  • Restart every PHP worker after updating or changing settings.

Timeline

  1. 17 October 2026

    AWS sees an exploitation attempt in its MadPot honeypots

  2. 20 October 2026

    CVE IDs circulate; PHP posts an advance notice

  3. 21 October 2026

    PHP ships fixes and advisories at 14:00 UTC, a day early

  4. 21 October 2026

    AWS reports PHP2Shell is "broadly exploited in the wild"

AWS says it is unclear whether the attempts it observed would have succeeded against real systems, and recommends investigating from at least 17 October. As of 22 October, no successful compromise of a real-world victim has been publicly documented. PHP2Shell is also not listed in CISA’s Known Exploited Vulnerabilities catalog (version 2026.10.21).

Technical summary

  • CVE-2026-109618 is an RCE via out-of-memory corruption. PHP exits out-of-memory errors with longjmp(). If memory runs out while request state is only partly initialised, shutdown can read or branch on invalid memory. An attacker can reach this through request input handling, including multipart parsing.
  • CVE-2026-109619 is an RCE via stale global state. Request-owned data can stay in worker globals after the request’s memory is freed, and a later request on the same worker can use it before normal initialisation. Confirmed early consumers are INI diagnostics and session upload progress. Impact includes use-after-free, memory disclosure, and remote code execution with the web worker’s privileges.
  • Both are unauthenticated and network-reachable, with a CVSS v4.0 score of 9.2 (AV:N/AC:H/AT:P/PR:N/UI:N). Exploit reliability depends on the build, extensions, frontend, and memory allocator layout.
