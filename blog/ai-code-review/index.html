AI Code Review for Security

Before merge, AI code review for security should identify a reachable vulnerability, explain the attack path and give the author enough context to fix it in the pull request. General AI code review is sold on speed: summarising pull requests, catching bugs, suggesting refactors and reducing reviewer load. Security review has a narrower bar.

Why general reviewers bury security comments

General-purpose AI reviewers mix security comments with style, tests, naming, documentation, maintainability and summary feedback, so the one comment that should block a merge can appear next to ten that are merely suggestions. Developers learn which tools generate noise, and once a reviewer is known for low-value comments, its real security findings get ignored.

Security review should keep its comments separate so they stay visible, and focus on questions like:

  • Can an attacker reach this path?
  • What trust boundary changed?
  • Did the PR weaken authentication, authorisation, validation, parsing or isolation?
  • Is the fix obvious from the comment?
  • Should this block the merge?

Formant is an AI-native offensive security company built by security researchers, and Formant Review reviews pull requests for security issues only. Each finding is an inline comment on the vulnerable line with the attack path, proof-of-concept details and the fix.

What a specific finding contains

A weak comment says “This may be vulnerable to injection.” A useful one says which parameter is attacker-controlled, where it flows, why the escaping or validation is insufficient, what impact that creates and which line should change. That needs repository context, because many security bugs cannot be understood from the diff alone. The reviewer has to know how routes are wired, which middleware runs first, what the auth model expects, where data is normalised and which internal helper functions are safe.

Evaluation checklist

Test with pull requests from your own repositories. Seeded toy examples are too easy, and the useful test is whether the reviewer catches issues your team would actually ship. Score each tool against the same standard:

  • Did it find something your current review would miss?
  • Did it post the finding inline on the vulnerable lines?
  • Did it explain the exploit path in terms of your application, beyond the vulnerability category and CWE text?
  • Did it avoid style and quality noise?
  • Did it understand the surrounding auth, tenancy and data-flow assumptions?
  • Does it cover business logic, auth, injection, prompt injection, secrets, supply chain and IaC risk?
  • Did the suggested fix match how your team writes code?
  • Can you set project-specific rules for trusted paths, internal conventions and known false positives, and does triage feedback improve later reviews?
  • Did the finding close once the remediation commit landed? Fixed findings that stay open become cleanup work.
