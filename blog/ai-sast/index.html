What Is AI SAST?
Contents
  1. What AI SAST should answer
  2. Where traditional SAST stops
  3. Why review at the pull request
  4. How to evaluate AI SAST tools
  5. Related pages

AI SAST is static analysis that reviews code the way a security engineer does: it starts with the change, reads the surrounding application, traces whether attacker-controlled input can reach a risky operation and decides whether the result is exploitable.

Most teams already have scanners, but many of their findings are hard to reproduce, detached from product behaviour or discovered after the pull request has moved on. Rules catch known patterns. AI SAST should also tell developers whether a change creates an attack path worth stopping before merge.

What AI SAST should answer

  • Did this pull request introduce a real vulnerability?
  • Is the vulnerable path reachable in this application?
  • What assumption made the issue possible?
  • What should the developer change before merge?
  • Can the tool tell when the fix has landed?

Where traditional SAST stops

Traditional SAST is strong at pattern matching and policy coverage. It finds known categories across a large codebase, especially when the rule is well defined. It struggles with context-heavy bugs: broken access control, business logic flaws, trust boundary mistakes, prompt injection, framework-specific auth behaviour and multi-step data flows that only become dangerous in the surrounding application.

AI SAST covers those cases only if the model has enough repository context to reason about the code path. A model that sees a tiny diff with no call graph, no auth model and no project rules will still miss the hard bugs. With that context, it catches issues such as:

  • A new endpoint trusts an internal-only header that is actually user-controlled.
  • A permission check protects the read path but not the mutation path.
  • A payment or subscription state can be skipped through an unexpected transition.
  • A prompt injection path crosses from untrusted user content into an agent action.
  • A serializer, parser or template function becomes dangerous only with a particular call chain.

These bugs survive broad static checks because they depend on intent more than syntax.

Why review at the pull request

The author still has the change in their head. A finding posted two weeks later into a backlog competes with everything else. A finding posted inline on the vulnerable line can be fixed while the code is still moving.

Formant is an AI-native offensive security company built by security researchers. Formant Review indexes repositories, builds codebase context and reviews pull requests for exploitable security issues before they merge. Each finding states what changed, how an attacker would reach the path and how to fix it.

Formant does not replace every scanner in a security programme. Dependency scanning, IaC checks, secrets detection and classic SAST still have a place. Formant adds the reviewer’s judgement on whether a code change creates an attack path worth stopping.

How to evaluate AI SAST tools

Ask whether the findings survive a developer’s first five minutes of scrutiny:

  • Does it review the pull request with broader repository context?
  • Does it explain exploitability, or only the category?
  • Can it learn from triage and project-specific rules?
  • Does it integrate where developers already review code?
  • Does it close or update findings after a remediation commit?
  • Can it show value on an existing risky code path in the first day?
