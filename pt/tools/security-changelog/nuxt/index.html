Quando um framework publica um alerta de segurança, esta página reúne o que as equipes precisam para priorizar patches: faixas afetadas, versões corrigidas, CVEs, alternativas, severidade e o alerta original. Lançamentos de funcionalidades e o ruído comum do changelog ficam de fora.

2026-10-30

  1. Dot segments in the request path bypass server/middleware path checks and server route rules on page routes

    Summary

    Since 4.6.0, Nuxt resolves . and .. segments in the request path, including percent-encoded forms such as %2e, before rendering a page. Nitro's routing, Nitro's route rules and server/middleware see the path with those segments still in place. A request for /%2e/admin therefore renders the page at /admin, while server-side checks keyed on /admin do not apply.
    • >= 4.6.0, < 4.6.3
    CVE-2026-119200
    Média

    Corrigido em 4.6.3
2026-10-22

  1. Nuxt server islands render useHeadSafe input without sanitisation

    Impact

    useHeadSafe restricts head input to an allowlist of safe tags and attributes. For example, bodyAttrs is limited to class and style, event handler attributes are removed, and <script> tags are only kept for JSON types.

    When useHeadSafe is called inside a server island (a .server.vue component or page, or a component rendered with <NuxtIsland>), the island renderer serialises the raw input of every head entry into the island response without the option that marks it as safe input.
    • >= 3.13.0, < 4.6.2
    CVE-2026-114133
    Média

    Corrigido em 4.6.2

  2. Incomplete fix for GHSA-934w-87qh-qr26: a javascript: URL prefixed with an ASCII control character executes from <NuxtLink> when pages is disabled

    Impact

    An application that renders <NuxtLink :to="..."> with a value it does not control can be made to render an anchor whose href executes script in the application’s origin when clicked.

    This is an incomplete fix for GHSA-934w-87qh-qr26 (CVE-2026-53722). It only affects applications running without a pages/ directory, where pages resolves to false and Nuxt registers its own router in place of vue-router.
    • < 4.6.0
    CVE-2026-114130
    Baixa

    Corrigido em 4.6.0

  3. Route rules are matched against the raw request path, so a percent-encoded segment can bypass appMiddleware on dynamic and catch-all routes

    Summary

    Nuxt compared routeRules keys against the raw request path, without decoding percent-encoding, while the router decodes parameters when it resolves a route. A request whose path is percent-encoded can therefore resolve to a page while failing to match the route rule meant to protect it, so the rule’s appMiddleware never runs, including during server rendering.
    • >= 4.0.0, < 4.4.4
    • >= 3.11.0, < 3.21.4
    CVE-2026-114131
    Média

    Corrigido em 3.21.4, 4.4.4

  4. Server-side route rules (redirect, headers, proxy, ssr) are skipped for case-variant paths when routing is case-insensitive

    Impact

    With the default router.options.sensitive: false, Nuxt’s page router resolves routes case-insensitively, so /Admin renders the same page as /admin. On the server, however, route rules were resolved with Nitro’s route-rule matcher, which matches keys case-sensitively. A request whose path differs from a rule key only in letter case therefore rendered the page with none of that rule applied.
    • >= 4.0.0, < 4.6.2
    • >= 3.0.0, < 4.0.0
    CVE-2026-114132
    Média

    Corrigido em 4.6.2

  2. Nuxt runtime payload cache discloses another user’s SSR data across users and to unauthenticated clients

    Impact

    When a page is covered by routeRules cache / swr / isr, Nuxt enables runtime payload extraction and serves /<page>/_payload.json. On affected versions the renderer stored the SSR payload in the shared cache:nuxt:payload storage under a path-only key (no cookie, authorization, or cache.varies dimension) and, on a later payload request, returned the cached entry before route middleware / page guards ran again.

    CVE-2026-71316
    Alta

  3. Unauthenticated CPU exhaustion parsing and hashing the Nuxt island endpoint body before hash validation

    Impact

    The internal island renderer endpoint (/__nuxt_island/...) decodes and hashes attacker-controlled request input before it validates the URL-resident hash. An unauthenticated POST /__nuxt_island/<name>_<anything>.json with a large JSON body (for example ~4.6 MB / 150k keys) is fully read, destr-parsed, and run through ohash before the request is rejected with a 400. Because Nitro runs on a single event loop, this both wastes CPU on the doomed request and delays every concurrent request.
    • >= 4.0.0, < 4.5.1
    • >= 3.1.0, < 3.21.10
    CVE-2026-71321
    Alta

    Corrigido em 3.21.10, 4.5.1

  4. Unauthenticated out-of-memory crash via unbounded v-for expansion in island rendering

    Impact

    An unauthenticated attacker can crash a Nuxt server that renders any island / server component containing a v-for over a prop (for example v-for="n in count" or a <slot v-for>). Because the island URL hash is a non-secret digest of the request, the attacker can compute a valid hash for arbitrary props and send the iterated prop as a large integer. The server then expands the v-for to that many nodes during SSR, allocating memory proportional to the attacker’s number.
    • >= 4.0.0, < 4.5.1
    • >= 3.1.0, < 3.21.10
    CVE-2026-71314
    Alta

    Corrigido em 3.21.10, 4.5.1

  2. Nuxt dev server vite-node IPC socket is world-connectable on Linux

    Impact

    When running nuxt dev on Linux (Node.js 20+, outside Docker / StackBlitz), Nuxt’s internal vite-node IPC server binds to a Linux abstract-namespace Unix socket (\0nuxt-vite-node-<pid>-<ts>.sock). Abstract sockets have no filesystem inode and therefore no permission bits: any local UID on the host that can read /proc/net/unix can enumerate the socket and connect to it.

    The IPC server does not perform any peer-credential or shared-secret check before dispatching requests.

  1. Dev server discloses project absolute path and persistent workspace UUID via /.well-known/appspecific/com.chrome.devtools.json

2026-05-29

  1. Nuxt’s route middleware is not enforced when rendering .server.vue pages via /__nuxt_island/page_*

    Summary

    When experimental.componentIslands is enabled (default in Nuxt 4), any .server.vue file under pages/ is automatically registered as a server island under the key page_<routeName> and exposed via the /__nuxt_island/:name endpoint. Until this fix, requests through that endpoint rendered the page component directly via the SSR renderer without instantiating Vue Router, which meant route middleware declared on the page (including definePageMeta({ middleware })) did not run.

  1. __nuxt_island endpoint does not bind responses to request props, enabling shared-cache poisoning

    Summary

    The /__nuxt_island/* endpoint accepts attacker-controlled props query/body parameters and renders any island component without verifying that the URL-resident hash (<Name>_<hashId>.json) was actually issued for those inputs by <NuxtIsland>. The hash is computed and embedded client-side but never validated server-side, so the same path can return materially different responses depending on the query.

  2. Reflected XSS in navigateTo() external redirect

    Summary

    navigateTo() with external: true generates a server-side HTML redirect body containing a <meta http-equiv="refresh"> tag. The destination URL is only sanitized by replacing " with %22, leaving <, >, &, and ' unencoded. An attacker who can influence the URL passed to navigateTo(url, { external: true }) can break out of the content="…" attribute and inject arbitrary HTML/JavaScript that executes under the application’s origin.
