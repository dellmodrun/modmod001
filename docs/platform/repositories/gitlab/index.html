    Choose an access level

    Formant supports two GitLab access levels. Choose the service account’s role by who will manage webhooks and repository clone credentials.

    Maintainer access is recommended and sets everything up automatically. GitLab requires Maintainer access to create project webhooks and read-only clone credentials, so with this role Formant manages both for the projects you select.

    Developer access needs manual setup. It lets Formant read merge requests and post review comments. A read-only deploy token gives Formant access to clone repositories, and a GitLab Maintainer or Owner configures the webhook separately. The service account stays at Developer access while someone with permission handles the setup steps that need a higher role.

    Prerequisites

    You need to be a Formant organisation admin to connect GitLab and manage its settings.

    A GitLab group Owner creates the service account. For Developer access, you also need someone with permission to create deploy tokens and webhooks: a group Owner for group-level setup, or a project Maintainer or Owner for project-level setup. The service account itself can keep Developer access.

    Configure access

    Open Service Accounts

    In GitLab, open the group you want to connect to Formant, go to Settings, and select Service Accounts.

    Create a service account

    Give the service account a descriptive name, such as “Formant”.

    Click Create.

    Choose the service account’s access level

    Grant the service account access to the group or projects you want Formant to scan.

    Maintainer (recommended)

    Grant Maintainer access. Formant creates project webhooks and repository clone credentials automatically.

    Developer

    Grant Developer access. After you connect, save a read-only deploy token and configure webhooks by hand.

    Formant detects the account’s access level automatically.

    Create a personal access token

    On the service accounts page, select the service account and click Manage access tokens.

    Click Add new token and enable api, read_api, and read_user, the scopes listed in Formant’s setup instructions. Set an expiration date and click Generate token.

    Why Formant needs each scope:

    Scope What Formant uses it for
    api Posting review comments and, with Maintainer access, managing webhooks and clone credentials
    read_api Reading project and merge request information, diffs included
    read_user Identifying the connected service account

    Warning

    Rotate the personal access token before it expires to avoid a service interruption.

    Connect GitLab

    In Formant, go to Integrations and click Connect under GitLab. Paste the personal access token and click Connect GitLab.

    Select projects

    Go to Repositories and select the GitLab projects Formant can access.

    With Maintainer access, webhook setup is automatic. With Developer access, complete the Developer access setup before you start scans.

    Connecting GitLab does not turn on merge request reviews. Once access is ready, enable Review for the repositories and branches you want covered.

    Developer access setup

    Follow these steps when the service account has Developer access. Formant shows Needs setup until you save a deploy token.

    Create a read-only deploy token in GitLab

    Ask a GitLab group Owner or project Maintainer to open the group or project and go to Settings, then Repository, then Deploy tokens. There, they select Add token, give it a name, enable only read_repository, and click Create deploy token.

    Copy both the username and the token before you leave the page. GitLab shows the token only once.

    Note

    A group deploy token covers the projects in that group. The token you save in Formant must cover every selected private project. A project deploy token works when you are connecting only that project.

    Save the deploy token in Formant

    Open Integrations, then GitLab, then Manage. Under Webhooks and deploy tokens, enter the Deploy token username and Deploy token, then click Save.

    Configure the webhook in GitLab

    In the same Formant panel, copy the webhook URL and Secret token.

    In GitLab, open Settings, then Webhooks, on each selected project and click Add new webhook. Paste the full URL, query string included, and paste the secret into GitLab’s Secret token field.

    Enable these triggers:

    • Push events
    • Merge request events
    • Comments

    Keep Enable SSL verification selected and click Add webhook.

    Tip

    On GitLab Premium or Ultimate, a group Owner can create one group webhook instead of a webhook on each project. Configure the webhook at the group level or the project level, not both, to avoid duplicate deliveries.

    Enable merge request reviews

    Enable Review for the selected repositories. Open or update a merge request to trigger a review.

    Note

    Saving a deploy token clears Needs setup, but does not check that you created the webhook. If reviews do not run, check the webhook URL, secret, and triggers in GitLab. If repository access fails, check the deploy token’s scope, expiration, and project coverage.

    Self-hosted GitLab and GitLab Enterprise

    Maintainer and Developer setup both work with self-hosted GitLab and GitLab Enterprise. Follow the steps above on your own instance.

    Note

    On self-managed GitLab, service accounts require GitLab EE, and by default only an instance administrator can create them. Administrators can also allow top-level group Owners to create them. Instead of a service account, you can use a personal access token from an existing user with the chosen access level and the same scopes.

    When you open the Connect GitLab modal in Formant, select Self-hosted / GitLab Enterprise and enter your instance’s base URL, such as https://gitlab.example.com, before you enter the token.

    • Your GitLab instance must be reachable from Formant over HTTPS with a valid TLS certificate.
    • GitLab installed under a URL subpath, such as https://example.com/gitlab, is not supported. Use the instance’s base URL.
    • For Developer access, use the webhook URL and secret that Formant shows for this connection.
